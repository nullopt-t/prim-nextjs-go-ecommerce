## 1. Why this run was bounded

This is a follow-up to the 50/150/300-VU report. Because the stack runs on a personal workstation, this run was deliberately capped to protect the machine:

- **Max 100 VUs** (one third of the earlier 300-VU peak).
- **20-second phases** with **4-second cooldowns** (total load time ~100 s).
- Host and database telemetry sampled roughly every 3 s throughout.
- No config, pool-size, or code changes were made; no restarts.

**Key shape:** throughput is already ~1,200 req/s at 10 VUs and plateaus at ~1,250–1,300 req/s. Adding 10× more workers (10 → 100 VUs) buys **no throughput**, only queueing: p99 rises from **76.6 ms to 551.2 ms** while p50 rises from 3.5 ms to 40.3 ms.

The capacity knee is therefore **between 100 and 150 VUs**: at 100 VUs p99 is still ~0.55 s, but the earlier 150-VU run reached p99 ~2.83 s. Around 100 concurrent requests is the last comfortable operating point on this configuration.

## 5. Rate limits ("rates") — verified live

The auth endpoints use a per-client-IP Redis sliding window. Verified against the running API after clearing only the test IP's limiter keys, using **a unique email per request** so business-level resend/verify caps did not interfere:

| Endpoint | Configured limit | Allowed before 429 | Behaviour at boundary |
|---|---|---|---|
| `POST /auth/challenge/start` | 5 / minute | 5 | request 6+ → `429`, `Retry-After: 60`, `X-RateLimit-Limit: 5` |
| `POST /auth/challenge/resend` | 3 / minute | 3 | request 4+ → `429`, `Retry-After: 60`, `X-RateLimit-Limit: 3` |
| `POST /auth/challenge/verify` | 10 / minute | 10 | request 11+ → `429`, `Retry-After: 60`, `X-RateLimit-Limit: 10` |

Rejected body:

```json
{"code":"RATE_LIMIT_EXCEEDED","message":"Too many requests"}
```

Redis `ZCARD` matched the allowed count exactly (5 / 3 / 10), confirming the sliding-window script is atomic and correct. Note that the **business layer has its own resend/verify caps per challenge** (same email), which also surface as 429 — so a same-email probe can look rate-limited before the IP quota is exhausted.

## 7. Conclusions and next steps

1. **Capacity statement:** ~1,000–1,300 req/s with p95 ≤ ~260 ms and p99 ≤ ~550 ms up to ~100 concurrent requests. Beyond that, latency degrades sharply.
2. **First experiment to try:** raise `MaxConns` from 25 → 50–100 and `GOMAXPROCS` from 4 → 12, then repeat the 100-VU phase. If p99 drops and throughput rises, the ceiling is configuration, not code.
3. **Remove benchmark artefacts:** give each VU its own user/cart so results are not dominated by a single shared cart row. The current curve is a deliberate worst case, not a realistic traffic mix.
4. **Add observability:** enable `pg_stat_statements`, record pool wait time and Go GC/pprof during runs. This will pinpoint pool queue vs lock wait vs query cost.
5. **Find the exact knee:** a short 100 → 125 → 150 VU ramp would locate it; that is still well below the earlier 300-VU peak.
6. **Unregistered routes:** `GET /products/{product_id}/variants` and `GET /admin/products/{product_id}/variants` still return Gin's raw 404 (route wildcard-name conflict).
