## 2. Workload and methodology

- The target list is the same one used by the earlier Go harness: every GET in `docs/public/public_swagger.json` and `docs/admin/admin_swagger.json`, plus curated mutations. It was exported with `./stress -json` into `targets.json` and is replayed by `stress.js`.
- **119 unique endpoint+method combinations** (56 GET, 23 POST, 19 DELETE, 17 PATCH, 4 PUT) across **515 weighted slots**.
- Auth uses Redis-seeded `ps` cookies: `sess_stress_customer_0001` for customer routes and `sess_stress_admin_0001` for `/admin/*`.
- Destructive routes are probed with **random UUIDs** or empty bodies, so the full handler/service/repository path runs while seeded rows remain intact.
- Self-resetting writes are included: cart add/update/remove/clear, checkout, coupon apply, wishlist add/remove, and `DELETE /cart`.
- Each VU starts at a random offset in the weighted slot array and then advances sequentially, spreading load across all targets while preserving the weights.
- Three 30-second phases ran at **50 / 150 / 300 VUs**. The customer cart was seeded with a freshly stocked variant before each phase, and the server deadlock counter was sampled before and after.
- Per-endpoint metrics are collected through dedicated k6 `Trend`/`Counter` metrics (including exact HTTP status-code counters), then written to JSON by `handleSummary`.
- 2xx aggregates 200, 201 and 204.

## 7. Defects found and fixed (validated by this run)

### 7.1 `PATCH /admin/orders/{id}/tracking` returned 500 instead of 404
The service mapped `pgx.ErrNoRows` to a typed 404, but the handler re-wrapped **every** error as `apierr.InternalServerError`, masking the mapping. Fixed to propagate the typed error, matching neighbouring handlers.
- File: `backend/internal/order/order_handler.go`
- In this run the route was probed with random order IDs; all responses were 404, never 5xx.

### 7.2 Concurrent checkout deadlocks (`40P01`)
Three interacting causes were fixed:
1. **Missing cart lock.** `LockCartByUserID` is now acquired before reading cart items, so same-cart checkouts serialize.
2. **Non-deterministic variant lock order.** Stock reservation sorts by `VariantID`, matching `CommitReservationsForOrder`.
3. **Child-first cart mutations.** `AddItem` / `UpdateItemQuantity` / `RemoveItem` / `ClearCart` now take `LockCartByID` first, enforcing one global order: **cart → cart_items / variants**.

- Files: `backend/internal/checkout/checkout_service.go`, `backend/internal/cart/cart_repository.go`
- Verification: **0 deadlocks** across all three k6 phases and 346 successful concurrent checkouts (orders rose from 939 to 1,285 during the run).

## 8. Open finding (not changed)

`GET /products/{product_id}/variants` and `GET /admin/products/{product_id}/variants` are implemented and documented but **never registered**, so they return Gin's raw `404 page not found`. The handlers read `product_id`, while the routers already use `:id`/`:slug` at the same position — Gin rejects differing wildcard names. Fixing this needs a parameter-naming/route decision, so it was left open.

## 13. Notes and caveats

- k6 was executed from the `grafana/k6:latest` image with host networking; the reported throughput is client-observed and includes k6's own per-request overhead.
- All VUs share one customer session and one cart, so cart/checkout paths intentionally contend on the same rows. This is the worst case for lock serialization and is a deliberate part of the test.
- The run created 346 additional orders/payments and consumed seeded inventory; the DB row counts in the environment table are post-run.
- The two backend fixes remain **uncommitted** at report time in 3 files: `order_handler.go`, `checkout_service.go`, `cart_repository.go`.
- The test targets the dev stack (`GOMAXPROCS=4`, `MaxConns=25`); absolute numbers are environment-specific.
